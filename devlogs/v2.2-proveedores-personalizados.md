# DTS v2.2 — Proveedores personalizados y catálogo dinámico de modelos

**Fecha**: 23/07/2026

## Motivación

Hasta v2.1 los proveedores estaban cableados en el código: Gemini, Ollama, Groq,
DeepInfra, Together, Anthropic y OpenAI. Cualquier endpoint nuevo (un servidor
local con vLLM, LM Studio, LiteLLM, un proxy corporativo o un proveedor cloud
emergente) obligaba a tocar el código fuente.

v2.2 hace dos cosas:

1. **Proveedores personalizados**: el usuario define nombre, URL base y tipo de API
   desde la GUI. DTS usa esa configuración para crear el proveedor en caliente.
2. **Modelos dinámicos**: cada clase de proveedor puede preguntar a su endpoint
   (`GET /models`) qué modelos ofrece, en lugar de depender de listas estáticas.

## Diseño

### Modelo de datos

```python
@dataclass
class CustomProviderConfig:
    name: str          # id único (también la clave en AppConfig.providers)
    label: str         # nombre visible
    api_type: str      # "openai" | "anthropic"
    base_url: str
    models: list[str]  # catálogo cacheado / editado por el usuario
    enabled: bool
```

- Se guarda en `AppConfig.custom_providers` (`%APPDATA%/dts/settings.json`).
- Las API keys de un proveedor personalizado viven en `AppConfig.providers[name]`,
  exactamente igual que las de un proveedor integrado. Esto reutiliza toda la UI
  de keys, la rotación y `get_active_keys()`.
- `ProjectConfig.provider` pasa de `ProviderType` (enum) a `str` para poder
  almacenar cualquier nombre de proveedor. `ProviderType` se mantiene como
  catálogo de ids integrados.

### Descubrimiento de modelos

Nuevo módulo `src/core/model_catalog.py`:

| Función | Endpoint |
|---|---|
| `fetch_openai_models(base_url, key)` | `GET {base_url}/models` |
| `fetch_anthropic_models(key, base_url)` | `GET /v1/models` (SDK) |
| `fetch_gemini_models(key)` | `client.models.list()` |
| `fetch_ollama_models(host, port)` | `GET /api/tags` |

Todas devuelven `[]` ante cualquier error y loguean un warning. Nunca rompen la
UI: los llamadores caen a una lista conocida.

### Clases de proveedor

- `OpenAICompatibleProvider.get_models()` consulta el endpoint en vivo; si falla
  usa `known_models` (los modelos del proveedor personalizado) o la lista estática.
- `AnthropicProvider` acepta `base_url`, `provider_name` y `known_models`; su
  `get_models()` intenta el catálogo en vivo y cae a `ANTHROPIC_MODELS`.
- `OllamaProvider.get_models()` sigue detectando modelos locales.

### Factory

`create_provider()` resuelve primero proveedores personalizados y después los
integrados. Para un custom:

```python
if custom.api_type == "anthropic":
    return AnthropicProvider(keys, custom.base_url, custom.name, custom.models)
return OpenAICompatibleProvider(keys, custom.name, custom.base_url, custom.models)
```

## Interfaz

### Configuración global → Proveedor de IA

- Botones **“+ Nuevo proveedor”** y **“− Eliminar”** bajo la lista.
- Al crear uno, se pide un nombre y se genera un slug (`mi_servidor_local`).
- Formulario del proveedor personalizado:
  - Nombre visible
  - Tipo de API (`openai` / `anthropic`)
  - Base URL
  - API keys (misma sección reutilizada)
  - Lista de modelos con: agregar manual, quitar, **“Cargar del proveedor”**
- Los cambios del formulario se persisten al cambiar de proveedor y al guardar.

### Proyecto → Traducir

- El selector de proveedores incluye los custom habilitados que tengan al menos
  una key.
- Nuevo botón **“Actualizar modelos”** junto al selector de modelo: consulta el
  catálogo en vivo en un hilo aparte y actualiza el combobox.
- Para custom sin catálogo aún, el combobox se llena con `custom.models`.

## Retrocompatibilidad

- Los `settings.json` existentes con `"provider": "gemini"` siguen cargando: el
  campo ahora es `str` y acepta cualquier valor.
- Proyectos con `"prompt"` guardado no se ven afectados.
- `AppConfig.from_dict()` tolera la ausencia de `custom_providers`.
- `ProviderType` sigue existiendo para código que lo importe.

## Uso rápido de un proveedor personalizado

1. **Configuración global → Proveedor de IA → + Nuevo proveedor**
2. Nombre: `Mi servidor vLLM`
3. Tipo de API: `openai`
4. Base URL: `http://localhost:8000/v1`
5. Agregar API key (cualquier valor si el servidor no la valida)
6. **Cargar del proveedor** o agregar el modelo manualmente (`meta-llama/...`)
7. Guardar, abrir el proyecto, pestaña **Traducir**, seleccionar el proveedor y modelo.
